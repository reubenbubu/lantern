# Lantern run, scoring and test-set commands

The build and test commands every issue needs (full check, quick check, formatting, one module, local database, Maven mirror) are in `CLAUDE.md`, Commands, which also states the requirements. Run everything from the repo root. A real model costs money, so run it only with the user's go-ahead.

- Launch a local run in one step (checks JDK 21, Docker and git, checks the database port is free, starts the database, builds the jar when it is missing or older than the app's sources, runs `analyze`; `--build-only` only does that): `scripts/launch.sh --llm-properties <llm.properties> [--mirror-properties <local.properties>] [--system <name>] [--title <title>] [--set <property>=<value>]... [<name>=]<path>...`; `--set lantern.llm.roles.<role>=<model>` serves one role with another model of the settings file for that run; `--db-only` only starts the database, and `--yes` skips the cost question (required when not at a terminal). Stop it with `scripts/teardown.sh` (`--purge` also deletes the data volume). Both respect `COMPOSE_PROJECT_NAME`; options are in `--help`. Builds of the analyzed repositories go to one store every checkout shares, `LANTERN_BUILDS` (default `~/workspace/lantern-builds`), so a commit already built is not compiled again; delete a build's folder there to rebuild it.
- **Runs that count: Claude through OpenRouter** (`docs/adr/0070-course-correction-measured-acceptance.md`, amendment for #737; `docs/adr/0102-batch-api-and-openai.md`, amendment for #754). Pass `--llm-properties .claude/skills/lantern-commands/llm-openrouter.properties` (Haiku for the high-volume roles, Sonnet for the reasoning roles and the support judge, Opus for the wording judge; requests pinned to Anthropic; no batching), with `ANTHROPIC_API_KEY` set to an OpenRouter API key, inside the command only, e.g. `ANTHROPIC_API_KEY="$(tr -d '[:space:]' < <key file>)" scripts/score-testsets.sh --yes --llm-properties ...`. The launcher accepts this in-repository file because it sets no key. Set up once on OpenRouter:
  - under Settings, Integrations (BYOK), add the owner's Anthropic API key, for Claude Haiku, Sonnet and Opus 5.5 only;
  - leave the key's shared-capacity fallback at its default, "Use shared capacity": when the key's allowance is empty or rate limited, OpenRouter's own Anthropic capacity serves the call, at OpenRouter credits and with a cold cache, and the call is recorded as `Anthropic, OpenRouter credits` (`run.json`, `byModel`, `servedBy`);
  - give Lantern's OpenRouter API key a credit limit, so a fallback cannot spend more than that.
  DeepSeek and other non-Claude models serve only smoke runs whose numbers are not reported as results.
- Sandbox builds download only from the Maven repositories in `lantern.sandbox.maven-repositories` (Maven Central by default; see `docs/adr/0023-configurable-maven-repositories.md`). To allow others, list them all in a properties file and add it to the app's: `--spring.config.additional-location=file:<repositories.properties>,file:<llm.properties>`.
- Run Summarize alone on project-4's classes through a real model (costs money; only with the user's go-ahead; #871): its facts come from a fake-model analyze of project-4, kept in the checkout's `workspace/llm-logs/inputs/project-4-fake` (make new ones with `scripts/score-testsets.sh --fake-llm --label <label> project-4`, free, when the facts' format changes); then `ANTHROPIC_API_KEY="$(tr -d '[:space:]' < <OpenRouter key file>)" ./mvnw verify -pl lantern-app -am -Dit.test=SummarizeOpenRouterIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false -Dlantern.test.summarize-run=$PWD/workspace/llm-logs/inputs/project-4-fake -Dlantern.test.project4=$HOME/workspace/lantern-test-projects/project-4 -Dlantern.test.summarize-description="<what the run tests, e.g. Baseline: today's format against Haiku through OpenRouter>" [-Dlantern.test.summarize-items=10 | -Dlantern.test.summarize-classes=$PWD/lantern-app/src/test/resources/summarize/project-4-hard-classes.txt (the classes where problems showed, for short runs)] [-Dlantern.test.summarize-cap=0.10] [-Dlantern.test.summarize-packet-items=4 [-Dlantern.test.summarize-packet-tokens=90000] [-Dlantern.test.summarize-thinking-per-item=1500]] (types share requests as the app packs them, #874) [-Dlantern.test.llm-properties=<settings file>]`. It uses `llm-openrouter.properties` (Haiku) unless told otherwise, spends at most the cap in US dollars, and writes the checkout's git-ignored `workspace/llm-logs/summarize/<time>-<description>/` (`-Dlantern.test.summarize-out=<folder>` puts runs elsewhere; a run writes into `current/` there while it goes on, to watch, and is moved to its own folder when it ends): `README.md` (the description, model, cap and inputs, written first), `report.md` and `report.json` (items, sentences answered and left out by check, answers sent back, tokens by kind, time, cost, the summaries), `calls/` (every request and answer, replayable for free with `lantern.llm.replay-from`) and `log/` (each call, as soon as it finishes, as a plain-text file to read, headed by the run's description: its tokens, time and cost, the system prompt, the request, the thinking when the provider returns it, and the answer).
- Run Investigate alone on a fixed panel of leads through a real model (costs money; start small and raise the cap bit by bit; #890): its facts come from a fake-model analyze, kept in the checkout's `workspace/llm-logs/inputs/project-<n>-fake` (make new ones with `scripts/score-testsets.sh --fake-llm --label <label> project-<n>`, free, and copy `extracted.jsonl.gz` and `linked.jsonl.gz` there); then `ANTHROPIC_API_KEY="$(tr -d '[:space:]' < <OpenRouter key file>)" ./mvnw verify -pl lantern-app -am -Dit.test=InvestigateOpenRouterIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false -Dlantern.test.investigate-run=$PWD/workspace/llm-logs/inputs/project-<n>-fake -Dlantern.test.investigate-repos=$HOME/workspace/lantern-test-projects/project-<n> -Dlantern.test.investigate-leads=$PWD/lantern-app/src/test/resources/investigate/project-<n>-panel.txt -Dlantern.test.investigate-description="<what the run tests>" [-Dlantern.test.investigate-limit=<first n leads>] [-Dlantern.test.investigate-cap=0.05] [-Dlantern.test.investigate-model=haiku] [-Dlantern.test.llm-properties=<settings file>]`. Each lead is checked as a run checks it (Mode A, with its retry), no unit or the system explored, on Haiku unless told otherwise, within the cap in US dollars. It reads code with the shell in its sealed container (ADR 0127; needs Docker, and builds the image the first time); `-Dlantern.test.investigate-tools=graph` uses the graph's tools instead. It writes the checkout's git-ignored `workspace/llm-logs/investigate/<time>-<description>/` (`current/` while it runs): `README.md` (what the run tests and what it writes), `live.log` (one block per turn as the run goes, each tagged `[NN]` with its conversation's number: tokens sent and written, cost, each tool call with its result's size and first 8 lines, rejected calls, any note to the model; an `END` line per conversation with how it ended, its verdict and the key's), `conversations/<NN>-<lead>.md` (each conversation verbatim: system prompt, tools, every message as sent and received), `report.md` and `report.json` (per lead: verdict or why none, turns, tokens by kind, tool calls, cost, finding; in all: answers sent back, tokens, time, cost; the guard and safety-stop counts and the rejected tool calls by reason; with a key, the verdicts against it per kind and in all, and the leads it got wrong with the key's why), `calls/` (replayable for free) and `log/` (each call as plain text as soon as it finishes). The key is project-8's when it holds every chosen lead, or `-Dlantern.test.investigate-key=<answer-key.json>`. Replay a recorded run for free, no key needed: add `-Dlantern.test.investigate-replay=<the run's calls/ folder>`, with the facts of the same set at the same pin (a fake-model run's documents folder). The panels are project-1 to project-3's first lead of each kind and twelve project-4 leads chosen for their kinds and the cases earlier runs found hard.
- Run the real-provider LLM test (costs money; only with the user's go-ahead), with `ANTHROPIC_API_KEY` already exported: `LANTERN_LLM_REAL_TEST=true LANTERN_LLM_REAL_TEST_MODEL=<model> ./mvnw verify -pl lantern-llm -am`
- Run the app (needs the local database): `./mvnw install -DskipTests && ./mvnw spring-boot:run -pl lantern-app`
- Analyze repositories end to end, one command for register, snapshot, build, extract, summarize, compose and render (needs the local database, Docker and the LLM settings of `docs/adr/0009-llm-configuration.md` in a properties file outside the repository; a real model costs money, so only with the user's go-ahead): `./mvnw install -DskipTests && java -jar lantern-app/target/lantern-app-*-exec.jar --spring.config.additional-location=file:<llm.properties> analyze [--system=<name>] [--title=<title>] [<name>=]<path>...`. The repositories form one named system, by default named after the folder they are all in; a repository belongs to one system, and `remove --system=<name> <repo>...` (instead of `analyze`) takes it out. It writes `workspace/documents/<system>/<snapshot>/<repo>.html` (Architecture Explorer), `<repo>.brief.html` (Executive Brief) and `<repo>.c4.html` (the `report-specs/c4-model-sequence-diagrams` report), and `_system.c4.html` (the same report for all repositories of the system as one system, titled by the system's title); see `docs/adr/0016-end-to-end-analysis-run.md`, `docs/adr/0031-report-spec-renderer.md`, `docs/adr/0044-c4-views.md` and `docs/adr/0071-named-systems.md`.
- Score a Lantern system report against a development set's reference (free, no LLM; `docs/adr/0072-scoring-harness.md`): `node lantern-web/scripts/score.mjs <report .c4.html or .json> testsets/<set> [--run <run.json>] [--out <prefix>]` writes `<prefix>.scorecard.json` and `<prefix>.scorecard.md` (default prefix: the report's path without `.html`). `run.json` is what `analyze` writes beside its documents: each role's provider and model, and the run's calls and cost. Compare two scorecards side by side: `node lantern-web/scripts/score.mjs compare <a.scorecard.json> <b.scorecard.json> [--labels <a>,<b>] [--out <file.md>]`. The scorecard also has a row per LLM role, read from `linked.jsonl.gz` and `llm.jsonl.gz` beside `run.json` against `testsets/<set>/answer-key.json` (`--answer-key <file>` names another; verdicts on drawn risks and connections the key does not settle come from `testsets/<set>/judgements.json`, or `--judgements <file>`, amendment for #748; `--warm <run.json>` and `--change <run.json>` add the warm rerun's and a one-file change's calls); `compare` adds the paired difference of their item scores and Investigate's spread between the two runs. Pool every set two score folders share, with the bootstrap interval and direction per set: `node lantern-web/scripts/score.mjs paired <scores/a> <scores/b> [--labels <a>,<b>] [--out <file.md>]`. Check an answer key, its form and every citation against git (with project-8's `investigate` section, each lead's verdict and evidence, #891): `node lantern-web/scripts/score.mjs check-key testsets/<set>/answer-key.json <reference.c4.json> ~/workspace/lantern-test-projects/<set>` (`docs/adr/0072-scoring-harness.md`, amendment for #667). Without Node 24 installed, use `lantern-web/target/node/node`, which the build installs.
- Measure extraction coverage, which reference items of a set the extracted facts back before linking (free, no LLM; `docs/adr/0089-extraction-coverage.md`): `node lantern-web/scripts/coverage.mjs <extracted.jsonl.gz> testsets/<set> [--out <prefix>]` writes `<prefix>.coverage.json` and `.md`; `extracted.jsonl.gz` is what `analyze` writes beside its documents. Check a set's map `testsets/<set>/coverage.json`, with the set's checkout for its citations: `node lantern-web/scripts/coverage.mjs check testsets/<set> [~/workspace/lantern-test-projects/<set>]`. `scripts/score-testsets.sh` runs it on every set it scores, and the full check on project-0 (into `lantern-app/target/project-0/`).
- Every run reads the LLM roles' prompts from `prompts/` (`docs/adr/0113-prompts-folder.md`): edit a file there and run again, no rebuild; only that role's items are asked again. Judge the owner's labelled wording texts with the wording judge's current prompts (real calls on the wording judge's model, reusing stored answers, so only with the user's go-ahead): `scripts/judge-labels.sh [--llm-properties <judge settings>] [--key-file <Anthropic key file>] [-- --split=tune|test|all --dimension=role|specific --labels=<folder>]` (defaults: `$LANTERN_JUDGE_PROPERTIES` and `$LANTERN_ANTHROPIC_KEY_FILE`, else the development VM's `~/workspace/lantern-llm-deepseek-judge.properties` and `~/workspace/anthropic.key`; it runs `scripts/launch.sh --judge-labels`); it prints how many texts the labels pass the judge passes, how many the labels fail it fails, and each text it got wrong.
- Run Lantern on the development sets project-1 to project-4 and score each (sets set up as below; starts the local database through `scripts/launch.sh`; a real model costs money, so only with the user's go-ahead): `scripts/score-testsets.sh --llm-properties <llm.properties> [--mirror-properties <local.properties>] [--role <role>=<model>]... [--tier <tier>=<model>]... [--label <name>] [--compare-with <earlier label>] [<set>...]`. It writes `workspace/scores/<label>/<set>.scorecard.json` and `.md`, the report and `run.json` in `<set>/`, and with `--compare-with` `<set>.compare.md`. An analysis is scored from the one folder of documents it wrote, or the script stops. `--score-only` scores the newest reports without analyzing, newest by when their `run.json` was written, not by folder number, which starts again from 1 after `scripts/teardown.sh --purge` (the sets need not be set up). `--fake-llm` instead of `--llm-properties` runs every role on a free fake model (Spring profile `fake-llm`; models `fake` and the priced `fake-priced`), so a whole run costs nothing. Each set's folder also holds `rejections.jsonl.gz`, every answer the checks rejected and every item dropped, with why (ADR 0100, amendment for #682). It also holds `flows.json`, each scope's flows chosen by the model and by rank on the same candidates, which the flow selection row scores side by side (ADR 0108, amendment for #743). `--record-calls` writes every LLM call of each run, request and response, to `workspace/scores/<label>/<set>/calls/` (ADR 0008, amendment for #529). Replay such a folder without calling a model (free; `docs/adr/0008-llm-provider-interface.md`, amendment for #759): `--set lantern.llm.replay-from=<calls folder>` with a settings file naming the recorded run's models and no API key. Each request with no recording fails and is logged; the 1F recordings are in `~/workspace/lantern-test-drops/1F/recordings-529/` (`d529-base/<set>/calls` for project-1 to project-4, `d529-p8/project-8/calls`), recorded on DeepSeek with `~/workspace/lantern-llm-deepseek.properties`. `--judge-wording` ends each run with the wording judge (`docs/adr/0111-wording-judge.md`; serve it with a model no writing role uses, `--role wording-judge=<model>`), whose verdicts (`wording.jsonl.gz`) the scorecard's judged rows read; draw the owner's label set from such a run's folder with `node lantern-web/scripts/wording.mjs draw workspace/scores/<label>` (writes `testsets/wording-labels/`). `--set lantern.harness.calibrate=<role>:<size>[,...] --set lantern.harness.calibration-trial=<label>` asks those roles again at that packet size for calibration, their answers kept apart (`docs/adr/0112-packet-size-calibration.md`). `--gates [--change-file <repo>:<path>]` follows each set's run with a warm rerun and a run after a one-line comment in one Java file, and the harness row checks both gates (`docs/adr/0072-scoring-harness.md`, amendment for #755); it triples the run's time, and on a real model the warm rerun costs nothing while the change costs what it re-asks. `--jobs <n>` analyzes up to n sets at once, each on its own database (compose project `<COMPOSE_PROJECT_NAME>-<set>` on a free port, stopped when the set ends with its data kept; its log in `workspace/scores/<label>/<set>.log`), with the same scorecards as one at a time; `--jobs 5` analyzes project-1 to project-4 and project-8 in about 130 s instead of 340 s on the development VM (#785). It refuses the held-out sets project-5 to project-7 unless `--held-out` is given, which is only for Phase 2's real-model acceptance (`docs/design.md`, Test sets).
- Run a set twice with the fake model, the second time with Summarize on another (priced) fake model, score both and compare them (free): `./mvnw verify -pl lantern-app -am -Dlantern.test.set=$HOME/workspace/lantern-test-projects/project-4 -Dit.test=TestSetScoreIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`; it writes `lantern-app/target/test-sets/<set>/`. A held-out set fails it unless `-Dlantern.test.held-out=true` (`docs/design.md`, Test sets).
- Run that pipeline twice on any Maven repository with the fake model, checking the second run makes no LLM calls, and write the calls and estimated tokens a real run would use to `lantern-app/target/end-to-end/`: `./mvnw verify -pl lantern-app -am -Dlantern.test.repo=<absolute path> -Dit.test=EndToEndIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
- Set up the synthetic test set project-0 at its pinned commit (private repository, so git needs GitHub credentials; see `docs/adr/0029-synthetic-test-set-project-0.md`), then build each of its repositories in the sandbox: `testsets/project-0/setup.sh && ./mvnw verify -pl lantern-sandbox -am -Dlantern.test.project0=$HOME/workspace/lantern-test-projects/project-0 -Dit.test=Project0BuildIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
- Set up the synthetic test set project-8 (FleetCare) at its pinned commit (private repository, so git needs GitHub credentials; `docs/adr/0029-synthetic-test-set-project-0.md`, amendment for #285): `testsets/project-8/setup.sh [destination]` makes its 15 repositories under `~/workspace/lantern-test-projects/project-8/` and puts its expected answers in `expected/` there. Analyze and score it with `scripts/score-testsets.sh --fake-llm [--mirror-properties <local.properties>] project-8` (free), and compare the scorecard with the committed baseline `testsets/project-8/baseline.scorecard.md`.
- Set up an open-source test set, project-1 to project-4 (development) or project-5 to project-7 (held-out: set them up only for the work that may touch them, `docs/design.md`, Test sets): `testsets/project-<n>/setup.sh [destination]` clones each repository in its `pins.txt` into `~/workspace/lantern-test-projects/project-<n>/` and checks out the pinned commit (format: `docs/adr/0029-synthetic-test-set-project-0.md`, amendment for #251). `./mvnw verify` checks, without network, that each committed reference in `testsets/<set>/reference/` is valid for the C4 report spec and describes the pinned commits (`lantern-web/test/test-set-references.test.mjs`).
- Check claim identity on every fact of a development set's snapshot (`docs/adr/0090-key-attributes.md`; analyzes it with the fake model, free; set up as below; writes facts and claims per predicate to `lantern-app/target/claims/<set>.tsv`): `./mvnw verify -pl lantern-app -am -Dlantern.test.claims-set=$HOME/workspace/lantern-test-projects/project-8 -Dit.test=ClaimIdentityIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`. project-0's end-to-end test in the full check runs the same check.
- Check the extractors' facts on project-0 (set up as above; reads the repositories from git, builds nothing): `./mvnw verify -pl lantern-extract -am -Dlantern.test.project0=$HOME/workspace/lantern-test-projects/project-0 -Dit.test='Project0*IT' -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
- Check the deployable units on project-0 (set up as above; builds each repository in the sandbox): `./mvnw verify -pl lantern-link -am -Dlantern.test.project0=$HOME/workspace/lantern-test-projects/project-0 -Dit.test=Project0DeployableUnitsIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
- Check the gateway routes of project-1, project-2 and project-4 (each set up with its `testsets/project-N/setup.sh`; reads the repositories from git, builds nothing; writes the lines to `lantern-link/target/gateway-routes/`): `./mvnw verify -pl lantern-link -am -Dlantern.test.projects=$HOME/workspace/lantern-test-projects -Dit.test=GatewayRoutesIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
- Check value resolution on project-8, deployment environments as views included (set up with `testsets/project-8/setup.sh`; reads the repositories from git, builds nothing, no Docker): `./mvnw verify -pl lantern-link -am -Dlantern.test.projects=$HOME/workspace/lantern-test-projects -Dit.test=Project8ValuesIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
- Check the Redis data stores of the test sets project-1 and project-4 (set up as in their `testsets/project-N/setup.sh`; reads the repositories named in `pins.txt` from git, builds nothing, no Docker): `./mvnw verify -pl lantern-link -am -Dlantern.test.projects=$HOME/workspace/lantern-test-projects -Dit.test=Project1And4RedisIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dfailsafe.failIfNoSpecifiedTests=false`
