# Code-level facts from Java source, and how accurate they are without a classpath

Research for #381 (Review the Java structure extractor), milestone "Extractor revisit". It asks what structure and call facts code-level architecture tools take from Java, how generated code changes what a reader sees, and how much accuracy a parse without the classpath loses against a full compile. It leads to an amendment of `docs/adr/0007-java-structure-extractor.md` and the Java structure row of `docs/design.md` (Static analysis and extractors).

**Depth: high.** The components, their dependencies and the flows rest on these facts. Read in full, 22 sources:

- 16 official docs or manuals (javac, JavaParser, Eclipse JDT, Spoon, Lombok, MapStruct, ArchUnit, jQAssistant, Spring, OpenAPI Generator, gRPC);
- 4 papers or thesis chapters;
- 2 practitioner sources.

Web pages came through a fetch tool that summarises as it reads; PDFs were read as extracted text. No published figure was found for JavaParser's or Spoon's accuracy without a classpath; the quantified evidence comes from PPA and VerveineJ/JDT. The research is generic: it does not read Lantern's test sets.

## Question

What structure and call facts do code-level architecture tools take from Java source? How accurate are those facts when the full classpath is missing? The facts in scope are:
- types, members, inheritance, annotations and stereotypes;
- calls through interfaces, dependency injection, lambdas, default methods and records;
- code generated by Lombok, MapStruct, OpenAPI and gRPC.

## What we learned

**Mature tools resolve against a compiler model, and most read bytecode.**
- ArchUnit imports compiled class files (`ClassFileImporter`). A call is recorded as an *access target*, not as a resolved member: "a `JavaFieldAccess` has no `JavaField` as its target, but a `FieldAccessTarget`".
- Resolution happens later and may return zero members (the declaring class was not imported) or several (a diamond, where "the call target … would in fact resolve to two `JavaMethods`").
- When ArchUnit cannot find a class it can stub it, but "this stub might naturally lack some information, like superclasses, annotations or other details".
- Annotations can be looked up by name without the annotation class on the classpath.
- Source: https://www.archunit.org/userguide/html/000_Index.html
- jQAssistant's Java plugin also scans `.class` files into a graph of Type, Method and Field nodes with the edges DECLARES, EXTENDS, IMPLEMENTS, INVOKES, READS, WRITES, ANNOTATED_BY and DEPENDS_ON.
- Types that are referenced but not scanned "will only provide the property `fqn` and the relation `DECLARES`".
- Dynamic dispatch is a separate rule, `java:VirtualInvokes`. It "propagates INVOKES relationships as VIRTUAL_INVOKES to non-abstract methods within the inheritance hierarchy" to identify "potential methods that could be invoked at runtime". `java:VirtualDependsOn` does the same for type dependencies.
- In jQAssistant, the static call target and the possible runtime targets are therefore two different facts.
- Source: https://jqassistant.github.io/jqassistant/current/

**javac sees everything, but only after annotation processing.**
- `JavacTask` exposes `parse()`, `analyze()` ("completes all analysis") and `generate()`, plus `Elements` and `Types` (https://docs.oracle.com/en/java/javase/21/docs/api/jdk.compiler/com/sun/source/util/JavacTask.html).
- Annotation processing runs in rounds. The files a round generates are inputs to the next round (https://docs.oracle.com/en/java/javase/21/docs/api/java.compiler/javax/annotation/processing/Processor.html).
- So MapStruct implementations, OpenAPI interfaces and gRPC stubs exist only after processing or code generation.
- Lombok is the exception: it changes classes in place inside the compiler. Lombok's own docs say that tools which read source directly cannot see what it generates. Its remedy is `delombok`, which writes plain Java and takes `--classpath` and `--sourcepath` like javac (https://projectlombok.org/features/delombok).

**What the common generators produce, and what a source-only reader therefore misses:**
- **Lombok `@RequiredArgsConstructor`** takes "one parameter per uninitialized `final` field and per uninitialized `@NonNull` field", in field declaration order. Annotations on fields reach the constructor parameters only if they are listed in `lombok.copyableAnnotations`, which is empty by default (https://projectlombok.org/features/constructor).
  - This is the most common form of constructor injection in Spring code. A parser that does not know Lombok sees a class with final fields and no constructor, so it sees no injection points.
- **`@Slf4j`** generates `private static final org.slf4j.Logger log = LoggerFactory.getLogger(X.class)`. The field name is configurable with `lombok.log.fieldName` (https://projectlombok.org/features/log).
- **MapStruct** generates an implementation of the `@Mapper` interface at build time; the examples name it `CarMapperImpl`.
  - With `componentModel = "spring"`, "the generated mapper is a singleton-scoped Spring bean and can be retrieved via `@Autowired`".
  - Mappers listed in `uses` are injected, by field by default.
  - Since Lombok 1.18.16 the extra `lombok-mapstruct-binding` processor is required, "otherwise MapStruct stops working with Lombok".
  - Source: https://mapstruct.org/documentation/stable/reference/html/
- **OpenAPI Generator (Spring):**
  - `interfaceOnly` generates only API interfaces.
  - `requestMappingMode=api_interface` puts `@RequestMapping` on the generated interface, so a hand-written controller only `implements` it and its endpoints are declared in generated code.
  - `library=spring-cloud` generates Feign clients, so outbound calls are also in generated code.
  - Source: https://openapi-generator.tech/docs/generators/spring/
- **gRPC Java:** `protoc` with the gRPC plugin generates the message classes and an `XxxGrpc` class with `XxxImplBase` and the stubs, "as part of the build". A server "extends the generated" `ImplBase`, and clients call `blockingStub.getFeature(...)` (https://grpc.io/docs/languages/java/basics/).
  - Both the server's supertype and the client's call target are generated types.

**Spring adds meaning that the plain Java facts do not carry** (https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html):
- **Stereotypes are meta-annotations.** `@Service` is meta-annotated with `@Component`. `@RestController` is "composed of `@Controller` and `@ResponseBody`". Composed annotations can redeclare attributes through `@AliasFor`.
  - Since Spring 6.1, custom stereotypes "must use `@AliasFor`" to set the bean name.
- **Scanning filters can make classes beans without any annotation.** Filters can be `assignable`, `regex`, `aspectj` or `custom`. Annotations alone therefore do not define the bean set.
- **Calls between `@Bean` methods differ by class.** In a `@Configuration` class they are intercepted by CGLIB and become references to the container's bean. In a `@Component` class they have "standard Java semantics".
  - `@Bean` methods "are also discovered on base classes … as well as on Java default methods declared in interfaces".
  - Calls to static `@Bean` methods are never intercepted.
- **Proxies decide which calls run advice** (https://docs.spring.io/spring-framework/reference/core/aop/proxying.html):
  - Spring uses JDK proxies when the target implements an interface, otherwise CGLIB, and "Spring Boot may … enable class-based proxies by default".
  - "Self invocation via an explicit or implicit `this` reference will bypass the advice". So `@Transactional`, `@Async` and other advice do not apply to inner calls.
  - With CGLIB, `final` and `private` methods cannot be advised.

**How much resolution is lost without dependencies (quantified).**
- **PPA** (Dagenais and Hendren, OOPSLA 2008) built a typed IR for each class alone and compared it with the whole-program IR on Lucene, JFreeChart, Jython and Spring 2.5.1 (https://www.sable.mcgill.ca/ppa/oopsla2008.pdf).
  - With one class and nothing else, a plain syntactic baseline got 81–89% of type facts correct. Adding type inference raised this to 88–94% (average 91.2%), with 2.7% wrong.
  - With the class plus its direct dependencies as source, the baseline rose to about 96% on average.
  - Spring, which needs 90 jars, stayed lowest (93.3% baseline, 95.0% with inference) "because a subset of the direct dependencies was contained in jar files which were not supplied".
  - The authors conclude that "adding the dependencies had a greater impact than type inference".
  - Most wrong facts came from the syntactic heuristics (up to 3.71% on Spring). The ambiguities behind them are undecidable without the declarations:
    - `E.m()` could be a static call on class E or a call on field E;
    - wildcard imports leave the fully qualified name unknown;
    - choosing an overloaded method needs the argument types.
  - The study used Java 1.4 only: no generics, lambdas or annotations-heavy code. It measured type facts, not call edges.
- **VerveineJ (Moose, built on JDT).** The maintainer explains that JDT links a call to its declaration only if it can resolve *all* parameter types, because overloading depends on them.
  - On ArgoUML, about 473 methods had problems without the library classpath and 13 with it (https://list.inf.unibe.ch/hyperkitty/list/moose-dev@list.inf.unibe.ch/message/FXWBJ4PTXJ3AZFC27WFSJUJMMNBNDHGX/).
- **Eclipse JDT.**
  - Bindings are off by default.
  - `setEnvironment` requires "all the required types" on the classpath or source path.
  - `setBindingsRecovery(true)` returns "incomplete bindings", flagged with `IBinding.isRecovered()`.
  - Source: https://help.eclipse.org/latest/topic/org.eclipse.jdt.doc.isv/reference/api/org/eclipse/jdt/core/dom/ASTParser.html
- **Spoon (built on the JDT compiler).** When neither source nor binary is present (Spoon's "noclasspath mode"), "both `reference.getDeclaration()` and `reference.getTypeDeclaration()` return null". The same holds for executables, so a call to an unknown method has no declaration.
  - A type available only as a binary becomes a reflection-built "shadow" type.
  - Source: https://spoon.gforge.inria.fr/launcher.html
- **JavaParser's symbol solver.**
  - It resolves "around the reference" (locals, then parameters, then fields) and "has not been written following the JLS".
  - Its handling of generics and lambdas "is not extremely robust and it does not work in 100% of cases" (https://github.com/javaparser/javaparser/wiki/About-the-Symbol-Solver).
  - A name it cannot find throws `UnsolvedSymbolException`. Facades and type solvers are single-threaded, and cached types go stale if the AST changes (https://github.com/javaparser/javaparser/wiki/Parsing-and-Symbol-Resolution-APIs).

**Even a full-program call graph from bytecode misses edges.**
- Sui's thesis, chapter 6 (the basis of Sui et al., ICSE 2020; https://mro.massey.ac.nz/bitstream/10179/16768/1/SuiPhDThesis.pdf), ran Doop on 31 real programs against edges seen in tests.
  - Median recall was 0.884: about 11% of known reachable methods were missed. Adding context sensitivity did not help (0.880). Reflection support raised recall to 0.935 on the 20 programs that finished within 6 hours.
  - `Method.invoke` explains under 10% of the misses. Dynamic proxies explain 0.42% and deserialisation 0.01%.
  - The largest causes are calls with no call site: invoked by the JVM, static initialisers, `finalize`, native code. One "double-reflective factory" pattern explains about half of the rest.
  - The corpus predates Java 8, so lambdas are under-represented.
  - The thesis also says tools "will continue to focus on particular usage patterns, such as support for reflection used in the Spring framework".
- The architecture-level counterpart: for Spring, the methods the framework calls without any call site are the entry points (controllers, listeners, `@Scheduled`, `@Bean`, `@PostConstruct`).

**Text-only microservice recovery reaches about 85% recall.**
- Code2DFD (Schneider and Scandariato, JSS 2023) greps source and config for keywords such as `@FeignClient` and follows identifiers across files ("snowballing"). It parses no AST and resolves no types.
  - On the validation set it reached 0.99 precision and 1.00 recall for services, and 0.96 precision and 0.84 recall for information flows.
  - Over all 17 apps it reached 0.94 precision and 0.88 recall. On their subsets, MicroDepGraph reached 0.99 precision and 0.58 recall, and Prophet 0.61 and 0.15.
  - Its stated limit: "direct keyword detection ceases to work reliably when developer-chosen identifiers are introduced" (https://arxiv.org/html/2304.12769v1).
- Cerny et al.'s review notes that static analysis "cannot determine how instances will be instantiated and interact". In microservices, though, deployment descriptors name the remote services and the remote calls are visible in the code, so a service dependency graph can be built from source. It names C4 as "a natural fit for microservices" (https://arxiv.org/pdf/2207.02988v1).

## Pitfalls for static analysis

1. **Lombok members are invisible to any reader that does not run Lombok.** `@RequiredArgsConstructor` constructor injection, `@Slf4j`'s `log`, builders and getters all disappear. Field annotations such as `@Qualifier` reach constructor parameters only through `lombok.copyableAnnotations`.
2. **Generated files exist only after a build:**
   - MapStruct `*Impl` beans;
   - OpenAPI interfaces that carry the `@RequestMapping` a controller inherits, and generated Feign clients;
   - gRPC `ImplBase` classes and stubs.
   
   A source-only read loses endpoints, server supertypes and outbound calls.
3. **Overloads cannot be resolved without every argument type.** JDT then binds nothing (VerveineJ). PPA calls method binding "undecidable because of overloaded methods" when declarations are missing.
4. **Missing jars hurt more than missing sources.** Spring was PPA's worst case, and ArgoUML went from 13 to about 473 problem methods without its jars. Types that are stubbed, shadowed or recovered lack supertypes and annotations, so inheritance and meta-annotation facts drop silently.
5. **Syntactic ambiguity:** class or field (`E.m()`), package or nested type, wildcard imports, `this` or the outer instance in inner classes. Heuristics are the main source of *wrong*, not merely missing, facts.
6. **The static target is not the runtime target.**
   - A call to an interface method resolves to the interface. Which implementation runs depends on overriding and, with DI, on the container: unique bean, `@Qualifier`, `@Primary`, `@Profile`.
   - ArchUnit returns 0..n targets, and jQAssistant adds VIRTUAL_INVOKES. Neither picks one.
7. **Calls with no call site.** Framework entry points, `@Bean` factories, listeners, scheduled jobs, static initialisers and JVM callbacks are the largest source of missed edges (Sui). They must be modelled from annotations and conventions.
8. **`@Configuration` calls between `@Bean` methods are references to beans, not new objects.** In `@Component` "lite" classes they are plain calls. `@Bean` methods may be inherited, including from interface default methods.
9. **AOP proxies.** Self-invocation bypasses advice, CGLIB cannot advise `final` or `private` methods, and JDK and CGLIB proxies behave differently. A static graph that draws "aspect advises X" holds only for calls through the proxy.
10. **Composed and custom stereotypes.** These need meta-annotation walking with `@AliasFor`. Scanning filters (`assignable`, `regex`, `custom`) can register beans that carry no annotation.
11. **Interfaces implemented at runtime.** Spring Data repositories, Feign clients and HTTP interfaces have no implementation in source. Calls to them end at a boundary that must be modelled as such. Sui finds dynamic proxies rare as a cause of missed edges in general Java, but they are central in Spring code.
12. **Lambdas and method references.** The JavaParser solver is "not 100%" on them, and invokedynamic is a separate feature in call-graph tools. A lambda's body runs when a library invokes it, possibly on another thread (`@Async`, executors, `CompletableFuture`).
13. **Keyword matching** breaks on identifiers that developers choose. Code2DFD's flow recall is 0.84.
14. **JavaParser engineering traps:** single-threaded facades, stale caches after AST changes, and exceptions instead of partial results.

## Options

| Option | Sees generated code | Call resolution | Needs | Trade-off |
|---|---|---|---|---|
| A. javac (`JavacTask` parse and analyze) on sources plus generated sources, with the build classpath and Lombok | Yes | Exact static target, JLS overloading, generics, lambdas | A successful build | Best accuracy; nothing without a build |
| B. Bytecode (ArchUnit or jQAssistant style) | Yes, as compiled | Static target from descriptors; lambdas as invokedynamic or synthetic methods | Class files | Exact like A; loses source ranges and generics detail; same build dependency |
| C. JDT batch with bindings recovery and whatever classpath exists | Not Lombok (unless delomboked), not generated files | Binds when all argument types resolve; recovered bindings are flagged | Partial classpath | Error-tolerant and marks uncertainty; heavy dependency |
| D. JavaParser symbol solver | No | Not JLS-conformant; throws on unknown names | Partial classpath | Light and pure Java; weakest on generics and lambdas |
| E. Spoon noclasspath | No | Declarations null when missing | Partial classpath | JDT underneath; no gain over C for this need |
| F. PPA-style inference on top of C or D | No | Infers missing declarations (+5 points of types in PPA) | — | Most errors come from its heuristics; not available off the shelf |
| G. Keyword or text extraction (Code2DFD) | Only what it greps | None | Nothing | About 85% recall on flows; brittle |

For the fallback path, closing the classpath gap (PPA: dependencies beat inference) and synthesising Lombok members are worth more than any choice among C, D and E.

## Recommendation (the researcher's)

Ordered by how common the pattern is in Spring Boot code and how much it changes components, their dependencies and the flows.

**Now**

1. **Record injection points and resolve them to beans.** This is the most common pattern and decides component dependencies.
   - For each bean, record each dependency it receives, whether by:
     - constructor parameter, including Lombok's `@RequiredArgsConstructor` parameters seen through javac;
     - `@Autowired` field or setter;
     - `@Bean` method parameter;
     - `ObjectProvider<T>` or `List<T>` injection.
   - Record each dependency with its declared type, any `@Qualifier` or `@Primary`, and the bean's `@Profile`.
   - Resolve the declared type, usually an interface, to the beans that can satisfy it: the scanned stereotypes, the `@Bean` return types, and the generated beans (MapStruct `componentModel=spring`).
   - Mark each resolution: *unique*, *chosen by qualifier, primary or profile*, *several candidates*, or *a framework proxy with no implementation in source* (repository, Feign, HTTP interface).
2. **Add dispatch edges next to the static target.** A call to an interface or abstract method declared in the analysed sources gets a dispatch edge to each overriding concrete method, as jQAssistant's VIRTUAL_INVOKES does.
   - Limit candidates to types that are beans or that the code instantiates (an RTA-like restriction). Prefer the target the injection resolution gives.
   - Keep the static target. The edge carries its resolution kind and candidate count, so a flow never shows a guessed implementation as certain.
3. **Treat generated sources as first-class but marked.**
   - Endpoints declared on a generated OpenAPI interface belong to the controller that implements it.
   - A class extending a gRPC `*ImplBase` is a gRPC endpoint, and calls on `*Grpc` stubs are outbound calls.
   - Generated Feign clients count as clients.
   - Mark generated types so they are never drawn as components of their own, but their edges are kept.
4. **Model calls the framework makes as entry points,** not as missing callers. Sui's largest source of missed edges is calls with no call site. The design's entry points (controllers, listeners, `@Scheduled`) cover most of this.
   - Add `@Bean` factories and `@PostConstruct`/`@EventListener` methods where they start work.
   - Treat calls between `@Bean` methods in `@Configuration` classes as bean references.
5. **Fallback path (failed build).** Synthesise Lombok's two common outputs instead of losing them:
   - `@RequiredArgsConstructor` (or `@Value`/`@Data`): parameters for final and `@NonNull` uninitialised fields, in declaration order;
   - `@Slf4j` and the other log annotations: the `log` field.
   
   Also:
   - Keep unresolved calls as facts with a "resolution: unresolved" mark and their name and argument count, rather than dropping them, so linking by name stays possible and is visibly lower in confidence.
   - Record each module's share of resolved calls, so a degraded module shows up in the quality report.
   - Feed the fallback every jar the failed build did resolve: the evidence says this matters more than any inference.

**Later**

6. **Asynchronous lambdas.** Attribute a lambda or method reference passed to `@Async` methods, executors or `CompletableFuture` to its enclosing member, which ADR 0007 already does. Then mark the edge asynchronous where the receiving method is a known async API.
7. **AOP precision.** Flag self-invocations of advised methods (`@Transactional`, `@Async`, aspects) as not advised, and do not draw advice on `final` or `private` methods under CGLIB.
8. **Beans registered by scanning filters** (`assignable`, `regex`, `custom`), and custom stereotypes whose name attribute is bridged with `@AliasFor`.
9. **PPA-style type inference** for failed builds, only if measured fallback coverage proves too low. It adds about 5 points of correct types at the cost of about 3% wrong facts.
10. **Reflection, serialisation and dynamic class loading.** Ignore them: they are rare causes of missed edges in Sui's data and expensive to handle.

## Decision

Lantern already takes option A with D as the fallback (ADR 0007), and on project-1..4 every Java fact comes from javac. Most of the recommendation is about what other steps make of these facts, outside this extractor; those parts are issues. What changes in the extractor now:

1. **Generated code is marked** (recommendation 3). Each type of generated code gets `generated`: the generator its `@Generated` names (MapStruct, OpenAPI Generator, gRPC and protobuf write one), or `build` for a type in the build's generated sources that names none. A member type takes its enclosing type's. Later steps can then keep generated types from being drawn as components while keeping their edges. On project-4, MapStruct's `*MapperImpl` classes are drawn as components today; leaving them out is #477.
2. **The fallback adds Lombok's constructors and log field** (recommendation 5, pitfall 1): `@NoArgsConstructor`, `@RequiredArgsConstructor` (and `@Data`) with a parameter per uninitialized `final` or `@NonNull` field, `@AllArgsConstructor` (and `@Value` or `@Builder` without another constructor), and the `log` field of each log annotation, as javac with Lombok declares them. A test checks both paths give the same constructors and log fields. Required-args constructors are the most common form of constructor injection in Spring code, so a module whose build fails no longer loses its injection points.

Issues, each where it belongs: injection points and dispatch resolved to beans, with a resolution kind (#478; recommendations 1 and 2); unresolved calls kept and each module's share of resolved calls reported (#479; recommendation 5); endpoints and calls in generated OpenAPI and gRPC code (#480); `@Bean` references and AOP self-invocation (#481; recommendations 4 and 7). Recommendation 4's entry points are already the design's (controllers, listeners, `@Scheduled`). Feeding the fallback every jar the failed build resolved is already ADR 0007's rule.

## What it changes in the bar and the design

- **Design, Static analysis and extractors:** the Java structure row says generated types are marked and the fallback adds Lombok's constructors and log field. ADR 0007 is amended.
- **Quality bar:** nothing yet. The researcher's proposals (a flow step resting on an interface call says which implementation it assumes; a document built from degraded modules says so) go with #478 and #479, where they are built.

## Researcher's notes on the bar and the design


Lantern's design already takes option A, with D as the fallback (`docs/design.md`, Java structure; ADR 0007). The research confirms that choice. Its "Why javac" paragraph matches the evidence on Lombok and generated code. Proposed changes:

- **Design: define "resolved call graph".** It should hold the static target (as now), plus dispatch edges and resolved injection edges. Each edge carries a resolution kind: direct, dispatch-unique, dispatch-several, bean-by-qualifier/primary/profile, framework-proxy, unresolved.
  - Add an injection-point fact: bean, declared type, qualifier, mechanism, resolved bean(s).
  - Component dependencies and sequence steps use injection or dispatch edges, and draw a step as certain only when its resolution is unique.
- **Design, Java structure fallback (ADR 0007 amendment):**
  - synthesise Lombok's required-args constructor and log field;
  - keep unresolved calls, marked;
  - report each module's share of resolved calls.
  
  ADR 0007 currently says "Lombok's members are missing, calls that do not resolve are left out".
- **Design, Spring extractor:**
  - entry points for a generated OpenAPI interface's mappings on its implementing controller;
  - gRPC `ImplBase` subclasses as endpoints and stub calls as outbound calls;
  - `@Configuration` calls between `@Bean` methods as bean references.
- **Bar:**
  - A dependency between components or a flow step that rests on an interface call must show which implementation it assumes and why (unique bean, qualifier, profile). When several are possible it must say so rather than pick one.
  - A document built partly from degraded modules says which ones and how much of their call graph resolved.
