# Draw runtime responsibilities, not build dependencies

A good architecture diagram lets a reader who has never opened the code answer five questions: what runs, what each running part or data store is responsible for, who or what talks to what, why, and over which protocol. Lantern's diagrams fail all five for one reason. They draw packaging (Maven modules, Java packages) and build-time "depends on" edges, which c4model.com explicitly says are "typically not" containers or components and are not valid relationship labels. The c4model.com container example works because every box is a runtime unit with a technology and a one-sentence job, and every arrow is a one-way runtime interaction with an intent phrase and a protocol ("Makes API calls to [JSON/HTTPS]"). Almost all the facts needed to reach that bar for OpenWMS are present in the code and config: deployable Spring Boot apps, `spring.application.name`, Feign clients, AMQP publishers and listeners, JPA repositories and datasources. The missing step is joining them across Java and YAML and across repositories. What code cannot supply is business purpose, people, rationale and production topology. The LLM should word these, and say plainly where evidence is missing. It should never invent edges. Sequence diagrams are worth generating only for a handful of cross-service flows, at a single C4 level. The written documents earn their place by saying what the code cannot: purpose, flows, where to change things, risk and decisions, each linked to evidence.

## Lantern's boxes and lines break four C4 rules at once

C4 defines a container as "a runtime boundary around some code that is being executed or some data that is being stored": a deployable app, a batch job, a function, a database schema, a bucket. Asked whether JARs and modules are containers, the site answers "Typically not" ([c4model.com container](https://c4model.com/abstractions/container)). A component is "a grouping of related functionality encapsulated behind a well-defined interface" inside one container. **JARs, modules, packages, namespaces and folders are packaging units that "may" map to components but typically do not** ([c4model.com component](https://c4model.com/abstractions/component)). For libraries and SDKs, C4 says you are "better off using something like UML" ([c4model.com FAQ](https://c4model.com/faq)).

The notation rules are just as direct. Every element needs an explicit type and "a short description, to provide an 'at a glance' view of key responsibilities". Every container and component needs a technology. Every line must be one-way and labelled with its intent, "ideally avoiding single words like 'Uses'", and lines between containers must name a protocol ([c4model.com notation](https://c4model.com/diagrams/notation)). A Maven aggregator drawn as `api`, `core`, `commons` and `service` boxes joined by "depends on" arrows therefore hits four anti-patterns together. Modules are drawn as containers. Libraries are drawn as containers. Labels state no intent. Edges follow compile direction instead of runtime calls. That is exactly the "nothing says who is responsible for what" complaint.

## Each C4 level answers one question for one reader

C4 gives each level a fixed scope and fixed elements, and says how strongly it recommends each one. The table condenses the official definitions ([context](https://c4model.com/diagrams/system-context), [container](https://c4model.com/diagrams/container), [component](https://c4model.com/diagrams/component), [code](https://c4model.com/diagrams/code), [landscape](https://c4model.com/diagrams/system-landscape), [dynamic](https://c4model.com/diagrams/dynamic), [deployment](https://c4model.com/diagrams/deployment)).

| Diagram | Question it answers | Reader | Must show | Typical failure |
| --- | --- | --- | --- | --- |
| Landscape | What systems does the organisation run, and who uses them? | Everyone | People and software systems in scope, no single focus | Containers leaking in |
| System Context | Who uses this system, and what does it depend on? | Everyone, including non-technical | One system in focus, user roles, directly connected external systems, no technology | Internals or protocols shown |
| Container | What runs, what does each part do, and how do the parts talk? | Architects, developers, ops | Apps and data stores, each with name, technology and job; protocol on every edge | Modules or libraries as boxes; one "message broker" hub |
| Component | Inside one runnable, which part owns X and what does it call? | Developers | Functional groups behind an interface, with technology and job | Packages drawn as components in a package-by-layer codebase |
| Code | How is this component implemented? | Developers | Classes and tables for one key component | Drawn at all for routine code |
| Dynamic | How do the parts carry out one feature? | Technical and non-technical | Numbered, scenario-specific interactions at one level | One per endpoint; mixed levels |
| Deployment | Where do the containers run in one environment? | Technical | Nested nodes, container instances, infrastructure nodes | Nodes invented without descriptors |

Context and Container diagrams are recommended "for all software development teams". Component diagrams only "if you feel they add value", and preferably automated. Code diagrams are "not recommended for anything but the most important or complex components", because IDEs generate them on demand. For a generator the effort argument disappears, so the bar for component diagrams becomes correctness: **a wrong component diagram is worse than none**.

Three C4 rules matter most for OpenWMS-style microservices. First, model each service as an API container plus its own database-schema container. Promote services to separate software systems only if separate teams own them ([c4model.com microservices](https://c4model.com/abstractions/microservices)). Second, **never draw the message bus as one container**. Draw each queue or topic as its own container, or write "via <queue>" on the producer-to-consumer arrow, because a single hub "hides which producer is coupled to which consumer" ([c4model.com queues and topics](https://c4model.com/abstractions/queues-and-topics)). Third, split crowded diagrams into several at the same level, for example one per service with its inbound and outbound neighbours ([c4model.com FAQ](https://c4model.com/faq)). Brown gives no element cap. Third-party guides suggest about 10 to 15 elements per diagram ([Visual Paradigm](https://skills.visual-paradigm.com/?p=971)). Treat that as a heuristic.

For components in Spring code, Brown's PetClinic example makes each web controller a component and groups the service and repository behind it. It leaves out domain and util classes ([c4model.com component](https://c4model.com/abstractions/component)). Automatic extraction works only when the code shows its architecture, through stereotypes, naming and package-by-component layout ([Brown, GOTO 2018](https://files.gotocon.com/uploads/slides/conference_12/515/original/gotoberlin2018-modular-monoliths.pdf)). The practical rule follows from that. Make one component per entry point (REST controller, message listener, scheduled job) plus the beans reachable from it. Treat packages as components only when the layout is by feature.

## Sequence diagrams pay off only for a few cross-service flows

C4 treats its dynamic diagram and a UML sequence diagram as two renderings of the same information, and recommends using them "sparingly to show interesting/recurring patterns or features that have a complicated set of interactions" ([c4model.com dynamic](https://c4model.com/diagrams/dynamic)). arc42's runtime view says the same: pick a small "representative selection" by architectural relevance and prefer schematic scenarios to detailed ones. It also widens the candidates to external interfaces, start-up and shutdown, and error handling ([arc42 section 6](https://docs.arc42.org/section-6/)). Neither source gives a number. Three to seven main flows per system, plus one or two error flows, is a reasonable reading, not a rule.

The research on generated sequence diagrams agrees on one failure: scale. Diagrams that show every call "rapidly become hard to navigate", and readers end up scrolling in two dimensions. Every workable approach collapses internals into their parent, filters out utilities, or caps depth ([Cornelissen et al. 2008](https://cms.simula.no/sites/default/files/publications/extravis-journal.pdf); [Hamou-Lhadj](https://www.eecs.uottawa.ca/~tcl/gradtheses/ahamou/AbdelwahabHamouLhadjPhDThesis.pdf)). For Lantern the equivalent filter falls out of the data model. Start at an entry point. Collapse everything inside one container into a single lifeline. Emit a message only where a call crosses a network, broker or database boundary. Then stitch across services: a Feign call continues into the callee's controller, and a publish continues into the listener bound to that exchange and key. A single-repo tool like the IntelliJ SequencePlugin cannot do that stitching ([SequencePlugin](https://github.com/Vanco/SequencePlugin)).

Labels should lead with intent and put the technology second, as in Structurizr's scenario-specific "Requests past orders from" ([Structurizr dynamic view](https://docs.structurizr.com/dsl/cookbook/dynamic-view/)). For example: "Create transport order [POST /transport-orders]" or "Announce order created [tms.events / to.event.created]". Drawing conventions follow UML. A synchronous call has a filled arrowhead, an async message an open one (Mermaid `-)`), and a reply is dashed. Draw replies only when they carry meaning ([Agile Modeling](https://agilemodeling.com/style/sequencediagram.htm)). Give each queue or exchange its own `queue` lifeline rather than one "RabbitMQ" lifeline. Add a note such as "later, asynchronously" after an async handoff, because neither Mermaid nor PlantUML can show time gaps ([Mermaid](https://mermaid.js.org/syntax/sequenceDiagram.html)). Use `alt` or `opt` fragments only for architecturally meaningful branches, such as failure plus compensation. Each diagram needs a title naming the scenario and its trigger, and two to four sentences of prose.

## Written docs must say what the code cannot

The oldest rule still governs: "Write documentation from the reader's point of view" ([Views and Beyond, Rule 1](https://www.informit.com/articles/article.aspx?p=1641654&seqNum=5)). Brown puts it more sharply: "describe what you can't get from the code" ([Brown guidebook](https://leanpub.com/documenting-software-architecture/c/free)). A sentence such as "`OrderService` is a service for orders" scores zero. A useful one says what the part decides, owns or protects, and what breaks if it changes. The Views and Beyond "view packet" pairs every diagram with an element catalog and context, so every box has a written answer to "what does it do?".

**For a new engineer**, Diátaxis explains why repo wikis feel useless. Mixing orientation, reference and how-to "is at the heart of a vast number of problems in documentation" ([Diátaxis](https://diataxis.fr/start-here/)). A practitioner comparison found DeepWiki well structured and linked to source, but "dense and overwhelming for newcomers". It explained "how" but not "why", and it repeated the same diagram across sections ([Bitovi](https://bitovi.com/blog/comparing-ai-documentation-engines-deepwiki-vs-code2tutorial)). The Explorer therefore needs four things in order. First, a short orientation: what the system is for and where to start. Second, the main request and message flows. Third, a reference catalog of containers, components, endpoints, queues, tables and config, each linked to source. Fourth, change guidance in the form "to add an endpoint, follow the pattern in package X".

**For a manager or architect**, Hohpe's point is that decision makers need "clarity, context, and strategic options", not detail ([Hohpe](https://eventfrog.at/en/p/courses-seminars/computer-it/masterclass-ride-the-architect-elevator-with-gregor-hohpe-7442081415737410244.html)). The Brief should lead with what the system does for the business, who depends on it and what it depends on (blast radius), technology currency, and risks ranked by cost. arc42 marks quality goals as the one thing always worth documenting ([arc42](https://docs.arc42.org/home/)). Code rarely states them, so the Brief should report quality evidence and say the goals are unrecorded. Ranking debt by real cost needs change history. Tornhill's hotspots are complex code that changes often, and rarely touched bad code is low-interest debt ([Tornhill SREcon24](https://usenix.org/system/files/srecon24emea_slides-tornhill.pdf); [CodeScene](https://codescene.com/blog/prioritize-technical-debt/)). A snapshot-only tool should say it cannot rank debt this way rather than present static smells as priorities. Rationale is what generators capture worst. Without it, newcomers fall into "blind acceptance or blind reversal" ([Nygard](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)). Surface ADRs and README rationale where they exist. Otherwise state the observed decision and mark the "why" as unknown.

LLM-generated docs add their own failure mode: confident errors. An OpenWrt maintainer reported DeepWiki producing "misleading architecture and dependency information" and wrong config descriptions, presented as authoritative ([OpenWrt forum](https://forum.openwrt.org/t/important-consideration-deepwiki-ai-generated-docs-may-contain-inaccuracies/249471)). Evidence on quality is thin. The best benchmark, CodeWikiBench, scores against rubrics derived from official docs using LLM judges, with about 71 to 74% rubric reliability and only a three-person human pilot ([CodeWiki, arXiv 2510.24428](https://arxiv.org/html/2510.24428v6)). The defence is structural. Ground every claim in an extracted fact, link it to source, and pin the document to a commit.

## Static extraction can recover OpenWMS's containers and edges

An independent 2024 evaluation ran 9 static architecture-recovery tools on 17 Java/Spring systems. **Only Code2DFD recovered both components and connections well (F1 0.86; connections 0.87)**, and most tools found almost no connections. Parsing deployment files gave high precision but low recall; recall needed deeper source analysis ([arXiv 2412.08352](https://arxiv.org/html/2412.08352v1)). Code2DFD's approach is many technology-specific extractors over code and config, with every model item traced back to a snippet ([arXiv 2304.12769](https://arxiv.org/abs/2304.12769)). Context Mapper detects connections only through `@FeignClient`. That narrowness explains its zero recall. Springwolf documents `@RabbitListener` consumers but cannot detect producers, because "there is no implementation uniform enough" ([Springwolf](https://www.springwolf.dev/docs/configuration/documenting-producers)). Spring Modulith's module canvas is a good template for per-component facts: stereotype beans, aggregate roots (entities with repositories), events published and consumed ([Spring Modulith](https://docs.spring.io/spring-modulith/reference/documentation.html)). Its events are in-process only, though, so it does not cover AMQP.

OpenWMS `org.openwms.tms.transportation` shows both what is there and where the joins are ([repo](https://github.com/openwms/org.openwms.tms.transportation)). The evidence for a container is concrete. The pom runs `spring-boot-maven-plugin` `repackage` with an `exec` classifier, there is a Dockerfile, and the service identity `spring.application.name: tms-service` sits in `bootstrap.yml`, not `application.yml`. The API is `TransportationController`, marked with the custom meta-annotation `@MeasuredRestController`, with paths taken from `TMSApi` constants. Services use `@TxService`, so stereotype matching must follow meta-annotations. Consumers are `@RabbitListener(queues = "${owms.commands.tms.to.queue-name}")` and similar. Publishers get the exchange from a constructor `@Value("${owms.events.tms.to.exchange-name}")` and pass literal routing keys such as `"to.event.created"` to `convertAndSend`. All the exchange and queue names live in YAML (`tms.events`, `tms.commands`, queue `tms-to-commands`, routing key `to.*`). Outbound HTTP comes from `@EnableFeignClients(basePackageClasses = {TransportUnitApi.class, LocationApi.class, ...})`. Those interfaces live in the *callee's* client jar, so the caller is whoever enables or injects them. The service's own `TransportOrderApi` is `@FeignClient(name = "tms-service")`, matching its application name. Persistence is JPA, through `TransportOrderJpaRepository` and a PostgreSQL datasource. Two blind spots are structural. AMQP is active only under the `ASYNCHRONOUS` profile, and the `DISTRIBUTED` profile pulls config from a central Config Service, so repo config is a default rather than production truth.

## Rubrics Lantern can test against

The authoritative version of these checks is the Quality bar in `docs/design.md`; this section is the evidence behind it.

Each check is yes or no. Most can be checked mechanically from the generated model, in the style of the official C4 review checklist ([c4model.com checklist](https://c4model.com/diagrams/checklist)).

**Every diagram:** a title naming type and scope ("Container diagram for Transportation"). A legend covering every shape, colour, line style and arrowhead used. One abstraction level. Roughly 15 elements or fewer, or split. Every element has a name, a type and a responsibility sentence that does not just restate the name. Every line is one-way, labelled with a verb phrase other than "uses" or "depends on", and linked to the code fact behind it. No acronym left unexplained.

| Diagram | Passes only if |
| --- | --- |
| System Context | Exactly one system in focus. User roles and external systems are directly connected. No technology. Unknown actors are marked unknown, not invented. |
| Container | Every box is a deployable app, job or data store, with `[technology]` and a job. No library modules, no packages. Each service's schema is its own cylinder. Queues and topics are their own elements or "via" labels, never one broker hub. Every edge is a runtime call with a protocol ("[JSON/HTTPS]", "[AMQP]", "[JDBC]"). Profile-gated edges are marked conditional. |
| Component | Scope is one container. Components are entry points with the beans behind them, carrying technology (e.g. "Spring MVC controller") and a job. Domain and util classes are left out. Edges leaving the container carry a protocol. Packages count as components only under package-by-component. |
| Code | Generated only on request, for one key component. |
| Landscape | All analysed systems and their people, with no internals. Edges are aggregated from container-level facts. |
| Dynamic / sequence | Names one scenario and its trigger. Participants are all from one C4 level and reuse the static diagrams' names. Only boundary-crossing messages appear. Labels put intent first and protocol second. Sync and async arrows are distinct, with a lifeline per queue. Returns appear only when meaningful. At most one level of fragments. Two to four sentences of prose. Three to seven per system, chosen because they cross services, hand off asynchronously or handle failure. |
| Deployment | Drawn only from real descriptors (Dockerfile, compose, Helm), one environment per diagram. Otherwise omitted with a note. |

| Document | Passes only if |
| --- | --- |
| Both | States its reader and pins the commit and date. Its first paragraph gives the system's purpose and the single most important fact. Every specific claim links to a source or fact. Unknowns (purpose, owners, rationale, quality goals) are stated once, plainly. No sentence that would be true of any Spring app. One name per concept across text, diagrams and glossary. No diagram repeated across sections. |
| Architecture Explorer | A five-minute orientation and "start here". Container diagram first. Main flows as sequence diagrams. A catalog of containers, components, endpoints, queues, tables and config with source links. Change guidance ("to add X, follow Y in Z"). Observed decisions, with rationale quoted from ADRs or README, or marked unknown. |
| Executive Brief | Business capability in one sentence. Upstream and downstream dependents (blast radius). Runtime and framework versions against end of life. Risks ranked by impact with a "so what" and a confidence. Activity level (active, frozen or abandoned). Quality evidence, with goals marked unrecorded if absent. The decisions or options the reader faces. No implementation detail. |

## What Lantern needs to extract to pass

Container facts come first. A container is a module with runtime evidence: a Spring Boot main class, a `repackage` or `exec` artifact, a Dockerfile. It is named by `spring.application.name`, resolved across `application*.yml` and `bootstrap*.yml` per profile. Library and client-classifier modules stay out of the boxes. Their code counts toward whichever container links them. Data stores come from datasource URLs, JPA entities and repositories, and Flyway or Liquibase schemas.

Relationships need four joins. First, resolve `${...}` placeholders against config. Where a placeholder cannot be resolved, keep the key name, which is itself meaningful. Second, fold constants for paths and routing keys, and follow a `@Value` constructor argument one hop into its `convertAndSend` call. Third, follow meta-annotations, so `@MeasuredRestController` and `@TxService` count as Spring stereotypes. Fourth, match across repositories. A Feign client name matches a target's `spring.application.name`. A publish to an exchange and key matches a queue bound to that exchange, with AMQP topic-wildcard matching for keys like `to.*`. The caller of a Feign interface is the service that enables or injects it, not the jar that defines it. Mark edges gated by `@Profile` as conditional. Treat Eureka, OTLP tracing and the Config Service as infrastructure, not business dependencies.

Components and flows reuse the same facts. Make one component per controller, listener or scheduled job plus the reachable beans. Trace each entry point inside its container and keep only the calls that cross a boundary. Stitch the traces across services into candidate flows, then rank them by how many services they touch, whether they hand off asynchronously, and whether they handle failure.

The LLM's job is narrow. It writes the responsibility sentence for each box, the intent phrase for each edge, the purpose of the system and the "start here", all from the extracted facts and the README. It may not add elements or edges, and anything it cannot ground is labelled unknown. Several things remain beyond the code and should be asked for or left visibly blank: people and roles, external systems such as PLCs or ERPs that are not referenced in code, owners, quality goals, rationale and production topology.

## Conclusion

Lantern's problem is not rendering or wording. Its model draws the wrong things. Its unit of analysis is the build graph, while every authority on architecture documentation starts from the runtime graph. Fixing the summarizer prompt will not help, because no description makes `commons` a container or "depends on" an intent. The good news is that Lantern's existing strengths, real builds, bytecode facts and source links, are exactly what the best-performing tools in the 2024 evaluation rely on. Spring's conventions make OpenWMS's runtime graph largely recoverable. The work is config resolution and cross-repo matching, not new analysis machinery.

Two consequences follow. The container diagram and three to seven stitched flows will carry most of the value for both readers, so they should come before more component or code detail. And because no one has validated a reader-level quality metric for generated architecture docs, the rubric above, checked mechanically on every run and with each claim traceable to a fact, is how Lantern can show that a document is right, not just plausible.
