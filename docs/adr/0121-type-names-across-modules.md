# 0121: Type names through `Types` in every module that reads facts

Status: accepted (#763)

## Context

ADR 0114 made the generated `Types` the one place that names vocabulary types, but checked only
the composer and the renderers. Derivation, the extractors, the linker, the LLM harness, the LLM
roles and the app still kept about 300 private copies of type names as constants and compared
predicates to string literals in about 70 more places. The extractors, the linker and the harness
could not use `Types`: it lived in `lantern-derive`, which depends on them. `docs/design.md`
wants one place that reads predicate names. The issue fixed the choice (owner may override): move
`Types` to `lantern-core` and widen the rule.

## Decisions

- **`Types` lives in `lantern-core`,** as `io.lantern.core.types.Types`, in a package of its own
  because the generator's check owns the whole folder it writes. `TypesTest` still runs in
  `lantern-derive`, the module that sees every vocabulary, and writes the class into
  `lantern-core` with `-Dlantern.records.write=true`. A new type is declared in its vocabulary
  file as before; the generator adds its constant.
- **The architecture rule covers every module that reads facts:** core, extract, link, derive,
  harness, summarize, compose and app (`ArchitectureRules.FACT_READERS`). No `static final
  String` there holds a type's name, read by reflection, so an alias of a `Types` constant counts
  too. Only `Types` itself is outside the rule.
- **The source check covers the same modules' main sources:** no relationship type's name written
  as a literal anywhere, and no type's name given to a fact query or written as a `case` label, as
  ADR 0114 set out.
- **Coincidences are named, not hidden.** A constant or literal whose value only happens to equal
  a type's name stays, listed with its reason in the rule (`NOT_TYPE_NAMES`) or the source check:
  command options (`--system`, `--title`), fields of an LLM role's answer (`responsibility`,
  `purpose`, `title`), attribute values (`by: datasource`, `via: java-release`, a component's
  role, a scope of `system`), an attribute key (`version`), a document block's kind (`table`,
  `diagram`), an SQL keyword (`REFERENCES`) and a Spring stereotype's value (`service`). Renaming
  the type must not change any of them.
- **The generated attribute records keep their `TYPE`** and count as part of the typed layer: they
  are generated from the vocabulary and checked against it as `Types` is (ADR 0090), and the
  linker's `Claims` reads `TYPE` to know which predicate a record reads. They hold the literal,
  not `Types.X`: `Types` is generated by a test in `lantern-derive`, which compiles only after the
  records do, so a record naming a new type through `Types` could never be generated. The rule
  passes a generated record's `TYPE`, and the source check skips the `attributes` packages.
- **The hand-written constants of `BuiltInTypes` go;** `Types` names the built-in types as it
  names every other one, and `TypesTest` already keeps it in line with the vocabulary files.

## Consequences

- Renaming or removing a type breaks compilation wherever code reads it, in every module.
- A fixture in a `io.lantern.link` package (`LinkerComparingPredicates`) shows both checks failing
  on a linker that copies a predicate's name as a constant and compares predicates to literals.
- Fake runs of project-0 and the five development sets are unchanged, document by document.
- Literals that are not in a fact-query position and are not relationship names (an entity type
  passed to a helper, say) are not caught by the source check; the constants rule and review catch
  most of them.
